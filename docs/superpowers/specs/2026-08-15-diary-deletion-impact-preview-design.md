# Preview de impacto antes de apagar episódio/temporada/série

## Contexto

Hoje `DELETE /diary/{id}` executa e retrai em cascata (`retractSeasonIfIncomplete`/
`retractSeriesIfIncomplete`, ou — depois do spec de rewatch — o wipe inteiro da série pra delete direto
de `SEASON`/`SERIES`) sem nenhum aviso prévio. O usuário só descobre o que sumiu depois de já ter
acontecido.

**Pedido:** antes de confirmar o `DELETE`, o frontend deve poder mostrar exatamente o que seria apagado
junto — ex. "excluir esse episódio apagará sua atividade: Temporada 3 concluída 12/03/2025" ou, se
também derrubar a série, "...e Série concluída 20/03/2025".

## ⚠️ Decisão necessária antes de implementar — NÃO começar sem isso resolvido

O pedido original incluía "apagará essa atividade (**incluindo review**)". Isso esbarra numa regra já
implementada e documentada (`business-rules.md` § DiaryEntry): uma vez que o usuário edita uma entrada
(`PATCH`, o que inclui adicionar nota/comentário), ela vira `autoGenerated = false` e fica **protegida**
de ser removida pela retração automática, pra sempre. Ou seja, hoje uma temporada com review de verdade
**nunca** está em risco de sumir sozinha.

**Você confirmou que quer que reviews também possam ser apagados** por essa cascata. Fazer isso sem
critério reabre um risco real: se a proteção cair de vez, um usuário que só corrigiu a data de um
episódio (sem intenção nenhuma de apagar nada) pode perder uma review de verdade como efeito colateral
de uma retração silenciosa que ele nunca viu vir.

**Solução proposta (ainda não aprovada — decisão sua):**

- O caminho **automático/silencioso** de sempre (delete de episódio sem passar pelo preview novo)
  **mantém a proteção como está hoje** — entrada editada nunca é removida por essa via, sem exceção.
- Só o caminho **novo desta spec** — depois que o preview já mostrou pro usuário exatamente o que seria
  perdido, review incluída — é que ele pode confirmar explicitamente e, só aí, a entrada revisada é
  removida junto. Confirmação explícita e informada troca por remoção antes impossível.
- Mecanismo: `DELETE /diary/{id}` ganha um parâmetro/flag de confirmação (ex.
  `?overrideProtectedEntries=true` ou corpo com um ack explícito) que só tem efeito nas entradas que o
  preview já listou como protegidas-mas-que-seriam-removidas. Sem esse flag, comportamento idêntico ao
  de hoje.

**Alternativa que você mencionou como possível preferência:** tirar a proteção de vez, em qualquer
caminho — inclusive fora do fluxo de preview (ex. um script, uma chamada direta a `DELETE` sem passar
pelo preview antes). Tecnicamente mais simples, mas reabre o risco de perda silenciosa descrito acima.

**Esta spec não deve ser implementada até você escolher entre as duas opções acima** (ou propor uma
terceira).

## Escopo: episódio isolado E delete direto de temporada/série

Cobre os dois fluxos, conforme decidido:

- **Delete de `EPISODE`** → preview da retração precisa (`retractSeasonIfIncomplete`/
  `retractSeriesIfIncomplete`, por `watch_number`, do spec de rewatch) — afeta no máximo uma passada de
  temporada e uma de série por vez.
- **Delete direto de `SEASON`/`SERIES`** → preview do wipe inteiro da série (decisão já tomada no spec
  de rewatch: apaga todas as passadas, todos os episódios, todas as temporadas). Esse fluxo é ainda mais
  destrutivo que o de episódio e merece o aviso mais que qualquer outro.

## Design: versão "dry-run" da retração

As funções de retração já calculam exatamente o que seria removido antes de remover
(`minCount`/`minMax` recalculado, lista de entradas com `watch_number` acima do limiar). A mudança é
separar **cálculo** de **execução**:

- `computeRetractionImpact(userId, ...)`: mesma lógica de `retractSeasonIfIncomplete`/
  `retractSeriesIfIncomplete` (ou do wipe de série inteira), mas só monta a lista do que seria removido —
  não chama `delete`.
- `retractSeasonIfIncomplete`/`retractSeriesIfIncomplete`/o wipe direto passam a chamar essa mesma função
  internamente e agir sobre o resultado — evita duplicar a lógica de cálculo entre o preview e a
  execução real.

## Novo endpoint

`GET /diary/{diaryEntryId}/deletion-impact` — não muda nada no banco, só devolve o que **seria** afetado
se aquela entrada fosse apagada agora:

```json
{
  "wouldDelete": [
    { "type": "SEASON", "watchedDate": "2025-03-12", "watchNumber": 1, "hasReview": true },
    { "type": "SERIES", "watchedDate": "2025-03-20", "watchNumber": 1, "hasReview": false }
  ]
}
```

`hasReview` (derivado de `comment`/`score` não-nulos) é o que permite ao frontend montar a frase
"incluindo review" só quando for verdade, em vez de sempre.

## Fluxo de confirmação

1. Frontend chama `GET /diary/{id}/deletion-impact` antes de mostrar o botão de confirmar exclusão.
2. Se `wouldDelete` vier vazio, `DELETE` normal, sem aviso.
3. Se vier algo, mostra a frase com as datas (e "incluindo review" se `hasReview = true` em algum item).
4. Usuário confirma → frontend chama `DELETE /diary/{id}` (com o flag de override se algum item tinha
   `hasReview = true` e a decisão pendente acima resolver exigir isso).

## Limitações assumidas

- Preview e delete são chamadas separadas — existe uma janela de corrida entre as duas (ex. o usuário
  apaga outra coisa em outra aba no meio do caminho) que pode deixar o preview levemente desatualizado.
  Aceito como baixo risco, mesmo padrão de qualquer preview-then-confirm.
- Não cobre a decisão de proteção pendente acima — nada disso deve ser codificado até ela ser resolvida.

## Testes

Bloqueados até a decisão acima ser tomada — o comportamento exato de `hasReview`/override depende dela.
