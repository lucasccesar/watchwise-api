# Rewatch de temporada/série no diário

## Contexto

Hoje `maybeCompleteSeason`/`maybeCompleteSeries` (`DiaryEntryServiceImpl`, feature de
`docs/superpowers/specs/2026-08-14-diary-season-series-completion-design.md`) criam a `DiaryEntry`
auto-gerada de temporada/série **uma única vez por usuário+conteúdo** — o guard em `maybeCompleteSeason`
(`if (diaryEntryRepository.findFirstByUserIdAndContentIdOrderByCreatedAtDesc(...).isPresent()) return;`)
nunca deixa uma segunda passada completa criar uma nova entrada. Reassistir uma temporada/série inteira
de novo não gera nada no diário além das entradas de episódio individuais.

**Pedido:** qualquer `Content` — `MOVIE` incluso, não só `SERIES`/`SEASON` — precisa conseguir dizer "eu
assisti isso X vezes". Pra `SERIES`/`SEASON` isso tem que contar passadas completas reais (todos os
episódios de novo), não só um log manual avulso.

## Duas coisas que pareciam uma só

Uma versão anterior deste spec cortou `MOVIE`/`EPISODE` de escopo, achando que dar a eles um contador
reabriria a complexidade de alinhamento entre passadas que motivou descartar a ideia original (um
`watchCount` por episódio dirigindo a cascata de completude). Esse corte era um engano — ele juntava duas
coisas que são independentes:

1. **Ter um contador em toda `DiaryEntry`**, de qualquer tipo, pra responder "quantas vezes logou isso" —
   é só `MAX(watch_number existente pra esse content) + 1` na criação, sem relação com temporada/série.
2. **Decidir completude de temporada/série** — isso usa **contagem de entradas de episódio** (`COUNT`),
   nunca o `watch_number` de um episódio específico. As duas coisas nunca se cruzam: o algoritmo de
   completude (seção abaixo) não lê `watch_number` de `EPISODE`/`MOVIE` em lugar nenhum.

Como não se cruzam, dar o contador pra `MOVIE`/`EPISODE` também não reabre o problema de alinhamento
entre passadas de episódios diferentes que motivou descartar a versão global antes — aquele problema só
existia enquanto a ideia era usar o contador do episódio *pra decidir* a passada da temporada. Sem isso,
sobra só um campo de exibição simples, igual em todo tipo de `Content`.

**Decisão: `watch_number` substitui `isRewatch` em toda `DiaryEntry`**, qualquer `content.type`.

## Modelo de dados

**`DiaryEntry` troca `is_rewatch BOOLEAN` por `watch_number INTEGER NOT NULL`.** Calculado pelo sistema
na criação, imutável depois — mesmo tratamento que `autoGenerated` já recebe hoje.

**Cálculo, em `persistDiaryEntry`:**

```
watchNumber = max(
    MAX(watch_number das DiaryEntry existentes do usuário para esse content) + 1,   // 1 se não existir nenhuma
    isRewatch == true ? 2 : 1
)
```

É a tradução direta da regra que `isRewatch` já segue hoje
(`isRewatch = alreadyLogged || Boolean.TRUE.equals(requestedIsRewatch)`): quando já existe pelo menos uma
entrada anterior, `MAX + 1` já sai `≥ 2` sozinho e o campo enviado pelo cliente nunca muda o resultado —
matematicamente equivalente a "ignorar o campo depois do primeiro log", sem precisar de um `if`
separado. Só no primeiro log (nenhuma entrada anterior) o campo importa: `isRewatch = true` empurra o
número pra nascer em `2` em vez de `1` (caso "já tinha assistido antes de começar a logar no app"). Não
dá pra declarar uma contagem retroativa exata (ex. "já vi 5 vezes"), só pular de `1` pra `2` — mesma
limitação que `isRewatch` (booleano) já tinha. Depois de criada, a entrada nunca tem `watchNumber`
recalculado — sem `PATCH` pra esse campo.

Vale igual pra toda origem de entrada — log manual do usuário (`MOVIE`, `EPISODE`, `SEASON`, `SERIES`) e
entrada auto-gerada pela cascata de completude (que nunca passa `isRewatch`, então cai direto no
`MAX + 1` puro).

**Migration nova** (`V12__replace-is-rewatch-with-watch-number.sql` — renumerar se
`docs/context/fixes.md` item 2 for implementado antes e ocupar o V12):

```sql
ALTER TABLE diary_entries ADD COLUMN watch_number INTEGER;

UPDATE diary_entries de
SET watch_number = sub.rn
FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY user_id, content_id ORDER BY created_at) AS rn
    FROM diary_entries
) sub
WHERE de.id = sub.id;

ALTER TABLE diary_entries ALTER COLUMN watch_number SET NOT NULL;

ALTER TABLE diary_entries ADD CONSTRAINT uq_diary_entries_user_content_watch_number
    UNIQUE (user_id, content_id, watch_number);

ALTER TABLE diary_entries DROP COLUMN is_rewatch;
```

O backfill usa a ordem de criação existente pra reconstruir retroativamente qual seria o número de cada
entrada — não tenta recuperar `isRewatch` diretamente, já que virar `watch_number` é estritamente mais
informativo (`isRewatch` velho vira `watch_number > 1` pra quem só quer o booleano).

**Corrida concorrente — duas regras, não uma.** O gatilho é o mesmo nos dois casos
(`DataIntegrityViolationException` na constraint `uq_diary_entries_user_content_watch_number`, quando
duas inserções concorrentes calculam o mesmo `watchNumber` pro mesmo par usuário+conteúdo), mas a reação
diverge conforme a origem da entrada:

- **Cascata automática** (`maybeCompleteSeason`/`maybeCompleteSeries`, `autoGenerated = true`): mesmo
  padrão de `ContentServiceImpl.getOrCreateReference` (`CLAUDE.md` § Idempotent get-or-create race
  conditions) — capturar `DataIntegrityViolationException` no insert, re-consultar por `(userId,
  contentId, watchNumber)`, tratar como já criada em vez de propagar erro. Correto aqui porque as duas
  linhas concorrentes são sempre equivalentes (`comment`/`score` sempre nulos, `autoGenerated = true`) —
  não existe payload do "perdedor" da corrida pra se perder.
- **Criação manual** (`POST /diary`, qualquer `content.type`): capturar a mesma exceção e mapear pra
  `ConflictException` (409), mesmo padrão que `uq_users_username`/`uq_users_email` já usam hoje
  (`CLAUDE.md` § Architecture → Data-integrity conflicts) — **sem** merge/re-consulta aqui. As duas
  linhas concorrentes representam submissões potencialmente diferentes (`comment`/`score`/`watchedDate`
  podem divergir); devolver ao chamador perdedor a entrada da outra requisição como se fosse a sua
  mascararia a perda do próprio payload dele sem nenhum sinal de erro. Cenário raro (dois cliques do
  mesmo usuário quase simultâneos, duas abas), mas quando acontece o cliente precisa de um 409 de
  verdade pra poder reagir, não de um corpo 200/201 que não é o que ele enviou.

## Algoritmo de completude (substitui `maybeCompleteSeason`/`maybeCompleteSeries` atuais)

Generaliza a lógica atual (que só reconhece uma passada) para reconhecer quantas passadas completas já
aconteceram, em loop — sem precisar que o chamador diga "qual passada", e **sem nunca ler o
`watch_number` de uma `DiaryEntry` de `EPISODE`** (só existência/contagem):

### `maybeCompleteSeason(userId, seriesTmdbId, seasonNumber, watchedDate)`

1. Busca o `Content` `EPISODE` com `isSeasonFinale = true` para essa série+temporada (igual hoje). Vazio
   → retorna.
2. `F` = número do episódio finale.
3. Query nova: contagem de `DiaryEntry` por `episodeNumber` do usuário nessa temporada (`GROUP BY
   content.episodeNumber`) — conta linhas, não olha `watch_number`.
4. `minCount` = mínimo, entre os episódios `1..F`, da contagem (`0` para qualquer episódio sem nenhuma
   entrada).
5. `currentMax` = `MAX(watch_number)` das `DiaryEntry` do usuário para o `Content` de temporada (`0` se
   não existir nenhuma).
6. Enquanto `currentMax < minCount`:
   - resolve/cria o `Content` de temporada via `getOrCreateReference` (igual hoje);
   - persiste a `DiaryEntry` de temporada (`autoGenerated = true`, `watchedDate` = a do episódio que
     disparou a chamada, `comment`/`score` nulos, sem `isRewatch`) — `watchNumber` sai como
     `currentMax + 1` pelo cálculo padrão descrito acima;
   - chama `maybeCompleteSeries(userId, seriesTmdbId, watchedDate)`;
   - `currentMax += 1`.

Com a API atual (sem endpoint de log em lote), um único episódio logado nunca faz `minCount` avançar
mais de uma passada por chamada — o loop roda no máximo uma vez na prática. Ele existe em forma de loop
mesmo assim para não depender dessa suposição silenciosamente.

`K = 1` reduz exatamente ao comportamento de hoje (uma passada, um guard de existência) — mesma
propriedade de regressão que o spec original já usava como sanity check.

### `maybeCompleteSeries(userId, seriesTmdbId, watchedDate)`

Mesma lógica, um nível acima: por temporada `1..G` (`G` = número da temporada finale, `isSeriesFinale`),
`MAX(watch_number)` das entradas de `SEASON` daquele número de temporada; `minMax` = mínimo desses
máximos; `currentMax` = `MAX(watch_number)` das entradas de `SERIES`; mesmo loop de criação.

## Retração (substitui `retractSeasonIfIncomplete`/`retractSeriesIfIncomplete` atuais, resolve item 4 do fixes.md)

### `retractSeasonIfIncomplete(userId, seriesTmdbId, seasonNumber)`

Chamado depois de apagar qualquer `DiaryEntry` de episódio dessa temporada.

1. Recalcula `minCount` (mesma query do passo 3/4 acima, já refletindo o delete).
2. Busca todas as `DiaryEntry` de temporada do usuário com `watch_number > minCount`.
3. Para cada uma **apenas se `autoGenerated = true`**: apaga, e chama `retractSeriesIfIncomplete` pra
   essa série. Uma entrada `watch_number > minCount` com `autoGenerated = false` (editada manualmente)
   é preservada — mesma regra de proteção que já existe hoje, agora resolvida por lookup exato em vez de
   "a mais recente".

### `retractSeriesIfIncomplete(userId, seriesTmdbId)`

Simétrico: recalcula `minMax` por temporada, apaga entradas de `SERIES` com `watch_number > minMax` e
`autoGenerated = true`.

**Consequência aceita:** se uma entrada manual ocupa um `watch_number` acima do que a completude real
sustenta (usuário criou a temporada na mão antes de logar os episódios correspondentes) e uma entrada
auto-gerada abaixo dela é apagada depois, pode sobrar um "buraco" na sequência — a entrada manual não é
tocada por estar protegida, mesmo estando numericamente acima de uma passada agora incompleta. Aceito
como o mesmo tipo de trade-off que a proteção de entradas manuais já aceita hoje (retração nunca mexe no
que o usuário editou, mesmo que isso deixe o estado "estranho").

## Apagar `EPISODE` vs. apagar `SEASON`/`SERIES` diretamente (redesenha item 3 do fixes.md)

Só existem duas granularidades de exclusão manual em `DELETE /diary/{id}` — decisão consciente pra
eliminar qualquer estado intermediário ambíguo (motivo detalhado abaixo):

- **`EPISODE`:** comportamento atual, sem mudança — apaga só aquela linha, depois roda
  `retractSeasonIfIncomplete` normalmente (a retração da seção acima já é precisa por passada via
  `watch_number`, sem ambiguidade nenhuma ali).
- **`SEASON` ou `SERIES`:** apaga o histórico **inteiro** daquele usuário pra aquela série — todas as
  entradas de `EPISODE`, todas as entradas de `SEASON` (de qualquer temporada da série) e todas as
  entradas de `SERIES`, em **todo `watch_number`** (todas as passadas), não só a passada da entrada
  clicada. Não existe "apagar só a temporada 2" nem "apagar só a passada 2" — apagar qualquer entrada de
  `SEASON`/`SERIES` é sinônimo de "esquecer que assisti essa série". Sem retração depois: não sobra nada
  pra reavaliar.

**Por que não é preciso por passada nem por temporada isolada:** ser preciso por passada exigiria usar o
`watch_number` do episódio pra decidir a qual passada ele pertence — voltando a depender do alinhamento
frágil entre episódios que a seção "Duas coisas que pareciam uma só" evita de propósito (dois episódios
da mesma série podem ser reassistidos em quantidades diferentes e fora de sincronia, então "os episódios
da passada 2" não é um conjunto bem definido). Escopar só a temporada clicada (preservando outras
temporadas da série) também foi cogitado e descartado: deixaria uma entrada de `SEASON` sobrevivente sem
nenhum episódio por trás dela sempre que uma passada intermediária daquela mesma temporada fosse apagada
— o mesmo tipo de estado órfão que esta seção existe pra evitar. Resultado: apagar qualquer
`SEASON`/`SERIES` é uma ação ampla e destrutiva por natureza — cabe ao frontend avisar o usuário antes de
confirmar.

**Repositório — métodos `@Query` em `DiaryEntryRepository`** (mesmo estilo JPQL já usado no arquivo):

```java
@Query("""
        SELECT de FROM DiaryEntry de
        WHERE de.user.id = :userId
        AND de.content.type = com.watchwise.watchwise_api.content.entity.ContentType.EPISODE
        AND de.content.seriesTmdbId = :seriesTmdbId
        """)
List<DiaryEntry> findAllEpisodeEntriesInSeries(
        @Param("userId") UUID userId, @Param("seriesTmdbId") String seriesTmdbId);

@Query("""
        SELECT de FROM DiaryEntry de
        WHERE de.user.id = :userId
        AND de.content.type = com.watchwise.watchwise_api.content.entity.ContentType.SEASON
        AND de.content.seriesTmdbId = :seriesTmdbId
        """)
List<DiaryEntry> findAllSeasonEntriesInSeries(
        @Param("userId") UUID userId, @Param("seriesTmdbId") String seriesTmdbId);

@Query("""
        SELECT de FROM DiaryEntry de
        WHERE de.user.id = :userId
        AND de.content.type = com.watchwise.watchwise_api.content.entity.ContentType.SERIES
        AND de.content.tmdbId = :seriesTmdbId
        """)
List<DiaryEntry> findAllSeriesEntries(
        @Param("userId") UUID userId, @Param("seriesTmdbId") String seriesTmdbId);
```

`findAllEpisodeEntriesInSeason` (do desenho original do item 3 do `fixes.md`) deixa de ser necessário —
como `SEASON` agora tem o mesmo alcance que `SERIES` (série inteira, não só aquela temporada), não sobra
nenhum chamador que precise filtrar por uma única temporada nesse fluxo.

`deleteDiaryEntry` — novo corpo:

```java
@Override
@Transactional
public void deleteDiaryEntry(UUID userId, UUID diaryEntryId) {
    DiaryEntry entry = findOwnedEntry(userId, diaryEntryId);
    Content content = entry.getContent();

    diaryEntryRepository.delete(entry);
    diaryEntryRepository.flush();

    if (content.getType() == ContentType.EPISODE) {
        retractSeasonIfIncomplete(userId, content.getSeriesTmdbId(), content.getSeasonNumber());
    } else if (content.getType() == ContentType.SEASON || content.getType() == ContentType.SERIES) {
        String seriesTmdbId = content.getType() == ContentType.SERIES
                ? content.getTmdbId()
                : content.getSeriesTmdbId();

        diaryEntryRepository.deleteAll(diaryEntryRepository.findAllEpisodeEntriesInSeries(userId, seriesTmdbId));
        diaryEntryRepository.deleteAll(diaryEntryRepository.findAllSeasonEntriesInSeries(userId, seriesTmdbId));
        diaryEntryRepository.deleteAll(diaryEntryRepository.findAllSeriesEntries(userId, seriesTmdbId));
    }
}
```

**Atenção:** `Content` do tipo `SERIES` guarda a chave própria em `tmdbId` (não `seriesTmdbId` — essa
coluna é `null` pra `MOVIE`/`SERIES`, só `SEASON`/`EPISODE` a usam).

## API / DTOs

- `DiaryEntryResponseDTO`: remove `Boolean isRewatch`, ganha `Integer watchNumber` (não-nulo, sempre
  ≥ 1) — nunca aceito em criação/update, só calculado.
- `DiaryEntryCreationDTO`: mantém `Boolean isRewatch` (nome e significado pro cliente não mudam — "eu já
  tinha assistido isso antes de logar no app"), só o efeito interno muda (empurra `watchNumber` pra
  nascer em 2 em vez de contar como booleano).
- `DiaryEntryUpdateDTO`: **remove** `Boolean isRewatch` — deixa de ser editável via `PATCH`, já que
  `watchNumber` é imutável depois da criação.
- `openapi.yaml`: `DiaryEntryUpdate` perde `isRewatch`; schema de resposta `DiaryEntry` troca `isRewatch`
  por `watchNumber`; `DiaryEntryCreation` mantém `isRewatch` como está.
- Sem endpoint novo. "Assistida X vezes" — pra qualquer `Content`, `MOVIE` incluso — é lido pelo cliente
  como `MAX(watchNumber)` entre as `DiaryEntry` daquele usuário+conteúdo, já disponíveis via `GET /diary`
  existente (equivale a `COUNT`, já que a sequência nunca tem buraco por criação — só pode ganhar buraco
  numa retração que preserva uma entrada manual de `SEASON`/`SERIES`, caso já descrito acima; não afeta
  `MOVIE`/`EPISODE`, que não têm retração). Não precisa de agregação nova — isso é escopo do futuro
  serviço de `Summary` (Fase 8), que já é responsável por agregações sobre `DiaryEntry` + `Content`.

## Limitações assumidas (fora de escopo)

- Delete direto de `SEASON`/`SERIES` apaga a série inteira do histórico do usuário (todas as
  temporadas, todos os episódios, todas as passadas) — não só a entrada clicada, nem só a temporada
  dela. Decisão consciente pra eliminar qualquer estado órfão, não lacuna (seção acima).
- `watchNumber` pode ficar com buraco na sequência se uma entrada manual "acima" sobreviver a uma
  retração de uma entrada auto-gerada "abaixo" dela (seção de retração acima) — só afeta `SEASON`/`SERIES`.
- Sem endpoint de log em lote hoje; o loop de criação de múltiplas passadas numa única chamada nunca é
  exercitado na prática, só existe por robustez.
- Migration é uma mudança quebra-compatibilidade no contrato de `DiaryEntry` (`isRewatch` sai da resposta
  e do `PATCH`) — aceitável porque o projeto ainda não tem consumidores externos, mas fica registrado
  como breaking change, não como evolução aditiva.

## Testes

Segue o padrão de cobertura já estabelecido (`CLAUDE.md` § Test coverage baseline):

- Unit tests de `persistDiaryEntry`: primeiro log sem `isRewatch` → `watchNumber = 1`; primeiro log com
  `isRewatch = true` → `watchNumber = 2`; segundo log (qualquer valor de `isRewatch`) → `watchNumber =
  MAX + 1`, ignorando o campo.
- Unit tests de `maybeCompleteSeason`/`maybeCompleteSeries`: primeira passada (regressão do comportamento
  atual, `watchNumber = 1`), segunda passada completa gera `watchNumber = 2`, entrada manual
  pré-existente ocupando um `watch_number` impede duplicata da cascata.
- Unit tests de retração: apagar episódio de uma passada antiga não mexe em passada mais nova já
  completa; apagar episódio que sustentava a passada mais recente retrai só essa; entrada manual acima
  do `minCount` recalculado é preservada.
- Unit/integração de `deleteDiaryEntry` pra `SEASON`/`SERIES`: apagar uma entrada de `SEASON`
  (qualquer `watch_number`) remove todos os episódios e todas as entradas de `SEASON`/`SERIES` daquela
  série, inclusive passadas anteriores completas e entradas editadas manualmente; apagar a entrada de
  `SERIES` tem o mesmo efeito; apagar um `EPISODE` isolado continua sem tocar em nada além do de
  costume (regressão do comportamento atual).
- Testes de integração ponta a ponta: completar uma temporada pequena duas vezes seguidas (dois
  rewatches completos) e verificar duas `DiaryEntry` de temporada com `watchNumber` 1 e 2 via resposta
  HTTP; apagar um episódio da segunda passada e verificar que só a entrada de `watch_number = 2` some;
  logar o mesmo `MOVIE` duas vezes e verificar `watchNumber` 1 e 2 na resposta.
- Corrida concorrente na constraint nova, duas variantes: (1) cascata automática — teste do mesmo padrão
  usado para `uq_contents_season_finale`/`uq_contents_series_finale` (item já coberto em
  `ContentServiceImplTest`/`ContentControllerIntegrationTest`), adaptado para
  `uq_diary_entries_user_content_watch_number`, confirmando que a segunda chamada não lança e retorna a
  entrada já criada pela primeira; (2) criação manual — confirmando que a segunda chamada propaga
  `ConflictException`/409 em vez de devolver a entrada da primeira.
