# Prompt de reavaliação ao completar temporada/série de novo

## Contexto

Hoje, quando o usuário loga o episódio que fecha a contagem de uma temporada (ou a temporada que fecha
a série), o backend cria a `DiaryEntry` auto-gerada correspondente por trás dos panos — mas a resposta
de `POST /diary` (a chamada que logou o episódio) não sinaliza isso em lugar nenhum. O cliente só
descobriria que a temporada fechou re-consultando `GET /diary` depois.

**Pedido:** quando essa auto-conclusão acontecer, o frontend deve poder mostrar um prompt do tipo "Você
terminou a X temporada pela Y vez! Deseja avaliar?" — **independente de qual episódio especificamente
completou a contagem** (o algoritmo já é assim: não importa a ordem de assistência, só que a contagem
bateu).

## Pré-requisito bloqueante: depende do `watch_number`

O "pela Y vez" só existe depois que
`docs/superpowers/specs/2026-08-15-diary-season-series-rewatch-design.md` (`watch_number` substituindo
`isRewatch`, completude reconhecendo múltiplas passadas) estiver implementado. Hoje o guard de
completude só cria a `DiaryEntry` auto-gerada de temporada/série **uma vez** por usuário+conteúdo — um
rewatch completo de uma temporada já concluída não gera nada novo pra avisar. Esta spec assume que o
redesenho de `watch_number` já está em produção; **não implementar antes disso**.

## Sinal de conclusão na resposta de `POST /diary`

Hoje `createDiaryEntry` chama `triggerCompletionCascade` mas descarta o resultado — `maybeCompleteSeason`/
`maybeCompleteSeries` são `void`. Para expor o sinal, essas cadeias precisam devolver as entradas que
efetivamente criaram nesta chamada (podem ser 0, 1 ou as 2 — logar o último episódio da última temporada
fecha temporada **e** série na mesma chamada).

**`POST /diary` passa a devolver um envelope novo** em vez do `DiaryEntryResponseDTO` cru:

```json
{
  "entry": { "...": "DiaryEntryResponseDTO da entrada que o usuário pediu pra criar" },
  "completedSeason": { "...": "DiaryEntryResponseDTO, só presente se esta chamada completou a temporada" },
  "completedSeries": { "...": "DiaryEntryResponseDTO, só presente se esta chamada completou a série" }
}
```

`completedSeason`/`completedSeries` só vêm preenchidos quando a auto-criação aconteceu **como efeito
direto desta chamada específica** — não é um flag persistente, é um sinal efêmero da resposta. Ambos
carregam `watchNumber` (do spec de rewatch), então o frontend monta "pela Y vez" direto do payload, sem
calcular nada.

**Escopo do sinal:** só dispara pra entradas `autoGenerated = true`. Se o usuário loga a temporada/série
manualmente (já preenchendo nota/comentário na mesma chamada), não faz sentido perguntar "deseja
avaliar?" depois — ele já está avaliando ali.

## Fluxo esperado no frontend (documentado pra o contrato fazer sentido, fora do escopo do backend)

1. Usuário loga um episódio.
2. Se a resposta trouxer `completedSeason`/`completedSeries`, mostra o prompt com o `watchNumber`
   correspondente.
3. Se o usuário aceitar avaliar, chama `PATCH /diary/{completedSeason.id ou completedSeries.id}` com
   `score`/`comment` — endpoint já existente, sem mudança. Efeito colateral já documentado e desejado:
   isso desliga `autoGenerated`, protegendo a entrada de retração automática futura — coerente, já que o
   usuário está afirmando de propósito que aquela passada importa.
4. Se recusar, a entrada continua `autoGenerated = true`, sujeita à retração normal se depois um episódio
   que a sustentava for apagado.

## API / DTOs

- Novo DTO de resposta: `DiaryEntryCreationResultDTO(DiaryEntryResponseDTO entry, DiaryEntryResponseDTO completedSeason, DiaryEntryResponseDTO completedSeries)`.
- `POST /diary` no `openapi.yaml`: schema de resposta troca de `DiaryEntry` pra esse envelope novo.
- **Breaking change** no contrato de `POST /diary` — aceitável pelo mesmo motivo que o resto do projeto
  já aceita mudanças de contrato hoje (sem consumidores externos ainda).

## Limitações assumidas

- Só sinaliza conclusão disparada por `POST /diary` de episódio/temporada — não existe (ainda) endpoint
  de log em lote que possa completar mais de um nível na mesma chamada além do já prático hoje (ver spec
  de log em lote, que quando existir também precisa emitir esse mesmo sinal, adaptado pra lote).
- Não avisa retroativamente sobre conclusões que já aconteceram antes desta feature existir — só entra
  em vigor pra cascatas futuras.

## Testes

- Unit tests de `maybeCompleteSeason`/`maybeCompleteSeries`: devolvem a entrada criada quando completam
  algo nesta chamada, `null`/vazio quando não completam nada, e as duas simultaneamente quando episódio +
  temporada completam na mesma chamada.
- Teste de integração: logar o episódio que fecha uma temporada e verificar `completedSeason` preenchido
  com o `watchNumber` certo na resposta HTTP; logar um episódio que não completa nada e verificar os dois
  campos ausentes/nulos; logar o episódio que fecha temporada e série ao mesmo tempo e verificar os dois
  presentes.
